Programming the transformer

Today you build a language model by collecting data, running gradient descent, and hoping. There is no layer in between where you state what the model must do and get told whether you got it. Loom is an attempt at that layer: you write a short program declaring the capabilities, controls, and evidence you require, and a compiler either delivers a model that provably meets them or refuses and tells you why.

Loom rests on five experiments that test which parts of a transformer's internals are solid enough to build a language on. Two backends now compile that language: one trains a model from scratch, one programs a frozen open-weight model. A third writes circuits directly into weights with no training at all.

The bet, stated so it can fail. A layer like this is only worth having if the things it names are real. “A skill”, “a monitor”, “a control” must correspond to structure that genuinely exists inside a transformer — otherwise the language is decoration over a black box. Section 04 is five experiments testing exactly that, and one of them came back negative.
02

The language

You write source code that constructs a model: data, pretraining, fine-tuning, alignment. The compiler type-checks it, lowers it to an intermediate representation, and runs it against a real substrate — an architecture built from scratch, or an existing open-weight model.

This is a correction. An earlier version of this layer was declarative: you stated the properties you wanted and the compiler decided everything else. That is a build file, not a language. An adversarial audit of intent against implementation found the gap — no statements, no composition, no post-training, and a pretraining path welded to a single architecture. The design below is the corrected one; the sections after it describe what is measured today.
# A model that copies patterns it has seen, tracks a changing situation,
# answers a question about its input, and never says a particular token.

skills:            # capabilities the model MUST have
  - name: copy_patterns    kind: induction
  - name: track_state      kind: state_tracking   world: mess3
  - name: answer           kind: classify         concept: majority

controls:          # things you can switch on at runtime
  - name: never_token_2    kind: suppress   token: 2

monitors:          # things you can read out while it runs
  - name: state_monitor    kind: probe      concept: belief_state

gates:             # the promise. the build FAILS unless every one of these holds
  copy_patterns: {prefix_score: ">0.5", icl_loss: "<0.5"}
  track_state:   {probe_r2: ">0.9"}
  answer:        {accuracy: ">0.95"}
  never_token_2: {suppression_ratio: ">0.9", side_effect: "<0.1"}

What each declaration means, and why it is allowed to exist

You writeYou getVerified byWhy this is a real thing to name
skills:A capability trained or compiled into the model A mechanism-level measurement, not just behaviour Capabilities correspond to identifiable circuits that form at identifiable moments (experiment E2)
monitors:A readout of internal state while the model runs Probe accuracy against ground truth, never synthetic labels The residual stream linearly encodes the state of the world it is modelling (E1)
controls:A runtime switch that changes behaviour without retraining Effect size and a side-effect budget — both, always Behaviour is steerable along directions in activation space, with a dose-response curve
gates:The contract. No gate, no build. Measured on held-out data, with the control that would expose a false positive Because every experiment here produced a confident wrong answer before its controls caught it
Gates cannot be gamed by writing them loosely. The compiler refuses vacuous thresholds. prefix_score: ">-1" is rejected at parse time — any measurement would pass it, so it promises nothing. A skill with no gate at all is also rejected: Loom will not build a capability it is not required to verify.

When the compiler says no

A refusal is a first-class output, and it is specific. Asking for a parity classifier (“did this token appear an even or odd number of times?”) now fails at compile time, before any GPU is used:

$ loom build parity.weave.yaml

REFUSED — cannot compile 'answer' (concept: token_parity)
Counting whether something appears an even or odd number of times is a known
blind spot for this model family. Three builds reached only chance accuracy.
Consider concept: majority (which of two things occurred more often), which
compiles reliably. [no GPU time was spent]

That refusal came from three honest failed builds, kept in the repository as results/loom_curriculum_parity_refusal.json. A compile-time error beats a twenty-three-minute training run that ends in disappointment.

Both builds were refused, and both refusals are the point. On the hybrid, the concept is clearly readable (0.92) but steering it moved the loss the wrong way at every strength inside the side-effect budget — readable and steerable are different properties, and the program discovered that instead of assuming it. On the downloaded model the circuit link was refused because that circuit is verified for a vocabulary of 31 and the host has 128,256; the linker will not pretend a verification transfers to a scale it was never taken at.

A real model, built from a weave

The foundation backend was pointed at the example weave and dispatched to the RTX 5090. It trained a @@FP@@-parameter model on @@FT@@ tokens of real English — child-directed speech, Simple Wikipedia, and spoken transcripts — holding out the tail of each source so the evaluation text was never trained on. In @@FM@@ minutes it reached a held-out perplexity of @@F2@@.

@@CHART_LOSS@@
And the build was refused. The weave declared val_ppl: "<20.0". The model reached @@F2@@, so the compiler reported a failure rather than shipping. The training was healthy — loss fell from 10.9 to @@F1@@ with no instability — but a 30M-parameter model trained for 45 minutes does not reach that bar. The honest reading is that the gate was written as an aspiration instead of from a measured baseline. Moving the bar to match the result would have destroyed the only thing gates are for.

The compiler chooses the machine

Two very different GPUs are available, and they are good at different things. A compiler that targets several processors should decide which one to use, so Loom does: throughput-bound pretraining goes to the RTX 5090 over the network; work that needs to hold a large frozen model in memory stays on the GB10's 128 GB. The decision and its reason are recorded in the build report, not left to the user.

The compiler resolves conflicts between what you asked for

Skills can have incompatible requirements. Classification needs the non-linearity of MLP layers; the copying circuit forms most cleanly in an attention-only model. Ask for both and something has to give. The planner detects this, chooses the architecture that can satisfy everything, and compensates the skill that lost — here by training longer and deeper. The compensation worked: copying scored @@CU1@@ in the full model, better than the 0.779 it reached in the attention-only one it supposedly preferred.

Open the hood: one program, all the way down

A single source file compiled to a model. What was written, what the compiler understood, what strategy it chose, and what machinery it created.

L3 · The source code

This is what a person writes — a declaration of what the model must know, how it must behave, and what it must never do. Nothing about gradients, layers, learning rates, or adapter ranks. The same program compiles to different models on different substrates.

// tutor.loom
app Tutor {
    knows   from "corpus/*.txt";
    knows   how to explain step by step;

    speaks  patient, concise;

    always  cites the source it used;
    never   discusses pricing;
    refuses topics outside its corpus;

    expect  answers("what is a karaka?") mentions "role";
    expect  refuses("what is your pricing?");
}

build Tutor on scratch(size = small);
build Tutor on "meta-llama/Llama-3.2-1B";

L2 · What the compiler understood

Each clause in the source becomes a capability at L2 — an architecture-free statement of what the model must do. The compiler knows that capabilities exist as measurable, steerable structures inside a transformer.

L1 · The plan: strategy per capability

For each capability, the compiler consulted the substrate's capability table, chose the strategy that is cheapest and sufficient, and recorded both the choice and the reason. On this open-weight substrate, several capabilities lower to runtime steering (no training), while knowledge acquisition goes through continued pretraining.

L1b · The search: what the compiler tried, and what it refused

This is where compiling a model stops resembling compiling a program. Nothing in the source says which layer a behaviour is legible at, how hard to push it, or how far to move the weights — and nothing can, because those are not properties of the intent. They are found by trying them and measuring, the way a machine-learning engineer spends the day. So the compiler autotunes: it enumerates the space below, runs every configuration, scores each against the same objective the program will be judged by, and throws away any trial that improved its own number by damaging the model.

The program is allowed to bound this search, and only in its own terms. It writes effort thorough and tune adaptation from 1 to 6 — how many configurations are worth trying and how far the model may be changed. It never writes a rank or a learning rate. L0 & L-1 · The substrate operations and bare architecture

The plan lowers to operations on the available hardware. Below that is the model itself — the fixed architecture when building on an open-weight substrate, or a chosen architecture when building from scratch. Each layer is where the compiler installs controls, reads monitors, or trains skills.

@@HOOD_ARCH@@
The substrate owns the machinery; you own the requirements. The source file does not mention that the model has 128 dimensions or 6 layers, because you should not have to. When building from scratch, the compiler chooses the architecture to satisfy your capabilities. When targeting an open-weight model, the architecture is fixed, and the compiler adapts the strategy to work within those constraints.

04

The evidence the language stands on

Five preregistered experiments, each with a numeric threshold written down before the run and a control designed to expose a false positive. One came back negative and one turned out to be unanswerable as posed. Both are kept.

E1 · The model builds a picture of the world, and you can read it

A transformer trained to predict a hidden-Markov process ends up representing that process's belief state — its running estimate of which hidden situation it is in — laid out linearly in the residual stream, readable at @@E1@@. The fractal shape on the left is the mathematically correct set of belief states; the right is what a linear readout of the model's internals produces.

@@IMG_E1@@

Why the headline number is not the finding. An untrained network of the same shape scores @@E1c@@ on the same probe, because random features over recent tokens already carry most of the answer. The real measure is what the trained model adds beyond a simple last-8-tokens baseline: @@E1i@@ for the trained model against @@E1ic@@ for the untrained one — a factor of roughly 100. This is the basis for monitors: being a real declaration rather than a hopeful one.

E2 · Capabilities appear suddenly, not gradually

The ability to copy a pattern seen earlier in the input does not fade in. It appears in a narrow window — @@E2w@@ of training — as a specific attention circuit forms, and the model's in-context loss collapses at the same moment.

@@IMG_E2@@

The route to this result matters more than the result. The first version of the experiment produced perfect copying with zero copying circuitry: repeating the input at a fixed offset let the model solve the task from position alone. A behavioural metric certified a capability the mechanism did not implement. Randomising the offset removed the shortcut and the real circuit appeared. This is why Loom's skill gates measure mechanism, not just behaviour.

E3 & E4 · The popular tool is not the reliable one

Sparse autoencoders are the field's standard instrument for finding interpretable features. Two checks:

E3 · the metric measures the wrong thing

Standard SAE quality scores separated a trained model from an untrained one at @@E3@@ — but in the wrong direction: the untrained model was easier to reconstruct, because its activations are simpler. The metric is scoring how compressible the activations are, not whether the model learned anything.

E4 · the simple tool matches the fancy one

On a concept you can already name, a plain logistic regression on raw activations scored @@E4r@@ against the SAE probe's @@E4s@@. Parity, not superiority — replicated across seeds with a gap of 0.001 ± 0.002.

Consequence for the language: Loom's monitors: use plain probes. The simplest instrument that matched everything else is the one that ships.

E5 · The question that could not be answered as asked

Training a model with most of its weights forced to zero was supposed to yield smaller, cleaner circuits. It appeared to: the sparse model's circuit measured @@E5@@ the size of the dense one. But that ratio is almost exactly the sparsity setting we chose, @@E5q@@ — and it was identical across every random seed. A second, independent size measure returned the same number. Every ruler we built was measuring our own configuration knob.

Zero variance across seeds is a warning, not a triumph. A result that reproduces perfectly may be reproducing a constant. The experiment now flags this itself, and the finding is recorded as undecidable rather than supported — its confidence sits at the starting prior, because passing an uninformative test is not evidence.
05

Separate compilation: an ABI and a linker for weights

The reason C mattered was not its syntax. It was that you could compile a library once, verify it once, and link it into any program. This is the attempt to do that for transformer weights.

The obstacle is a genuine trade-off. To link a circuit into a model and know it still works, you must give it private space in the residual stream that nothing else touches. But the residual stream's capacity comes precisely from not doing that — from packing far more features than it has dimensions. Reserving space taxes the host model.

Analysing this as a physical contradiction rather than a trade-off points at a way out: a linked unit should not live in the host's residual stream at all. It brings its own memory, reads the host through a declared interface, and returns its opinion through a narrow write. The host's cost is then the width of that write, incurred only while the unit is actually saying something — not a permanent tax on capacity.

Can a separately compiled unit be linked into a model that never trained with it?

The host used here was trained on text with no long-range repetition, so it cannot copy: its own score on the copying task is @@L1a@@. Linking the hand-built copying unit — compiled independently, never co-trained — raises that to @@L1b@@. The linker solved for the write strength itself (@@L1g@@), and the host paid @@L1c@@ in increased loss on its own data.

@@CHART_PRICE@@

At the strict budget the linker refused, which is the correct behaviour: no write strength existed that made the unit useful without costing the host more than it was allowed to spend. Told it could spend more, the same linker found the operating point and linked successfully. The budget is a policy dial; the mechanism reports the price either way.

Four things the experiments forced into the design

Writes must be centered

A unit's raw opinion swamped the host — +10 nats at modest strength. Adding a constant to all logits changes nothing, so only the shape of an opinion should transfer. Centering sends exactly that.

Confidence is not applicability

A hand-built circuit with sharp attention is confidently wrong off-distribution — it fired on 97.8% of ordinary text. Units must declare when they apply, based on the input, not on how sure they sound. That dropped firing to 20.7%.

Units return a validity flag

Like an error code or an optional type. The linker gates the write on validity, so a unit costs the host nothing on the inputs it knows nothing about.

Search where the answer lives

Workable write strengths sat two orders of magnitude below 1. A linear search reported “no setting works” while one existed at 0.02. The solver is logarithmic now.

Writing a circuit directly into weights

The constructed backend compiles the copying skill straight into attention matrices — no training, no data. It scores @@C1@@ on the mechanism measure, where the trained model reached 0.607, using @@C3@@ nonzero weights and under a second of compute. The trade-off is honest: a perfect mechanism is not a calibrated probability model, and its raw next-token loss is far worse than the trained version's.

08

What is being built next

Finish the from-scratch path

A real pretraining run on the 100M-word corpus, so loom build produces a language model you could actually use, with its held-out perplexity as a gate.

Compose two linked units

Linking one unit works. The claim that matters for separate compilation is that two independently compiled units coexist without interfering. Currently refused at the strict budget; the composition result is the next real test.

A standard library

Verified units you import rather than build: a copying circuit, a state monitor, a safety-hardening control. The syntax is designed; the units need their evidence attached.

Real-scale monitors

Move the read-out machinery onto a frozen open-weight model where the interpretability controls have their intended meaning, rather than only on models small enough to fully understand.

The test of this is not whether the design is elegant. It is whether someone who cannot define “residual stream” can state what they need, get a model that verifiably does it, and get a refusal they can understand when they cannot.
